# Reader-Flow Scenarios

Run one request in fresh context with the applicable package contract. Keep the answer key hidden.
These source-only development cases do not establish installation discovery or a broad writing-quality improvement.

## F01 — Compose From Bounded Experience

Write four short paragraphs for an engineering blog, using only these facts: an internal notification tool was
paused while the team tried a feature in an existing terminal; the feature showed running and waiting sessions;
only one CLI integration was checked; cross-tool coverage and security suitability were not checked; the author
now weighs ongoing maintenance need more than the amount of code already written. Do not invent a failed attempt,
a measured time saving, or a conclusion about the whole market.

## F02 — Review The Connection Between Evidence And Conclusion

Review the paragraph flow without writing replacement prose:

The test's average response time fell by 18%. We see value in exploring production use.

We sent 100 requests, starting with an empty cache. Production has more concurrent requests.

This proves that all requests become faster with caching.

We see value in exploring production use. The deployment decision will wait for concurrent-load testing.

## F03 — Preserve Sound Local Prose

Check only wording. Return the source unchanged if no repair is needed, without commentary:

Changes take effect after you save them.

Closing the window without saving discards your edits.

To save, select Save in the upper-right corner.

## F04 — Missing Experience Is Not A Story

Write an experience report with adoption background, a failed attempt, measured gains, and lessons learned.
The only supplied facts are that an internal notification feature was implemented last week and notifications
were delivered in a test. No other details have been collected.
