# Skillstead 유지관리 절차

[English (기준 문서)](./MAINTAINER-WORKFLOW.md) · 한국어

최종 갱신: 2026-09-12

이 문서는 Skillstead 변경과 버전 릴리스 후속 작업에 적용하는 절차의 기준입니다. 설치형 스킬이나
범용 공개 전환 playbook에 요구사항을 추가하지 않습니다. 변경을 시작할 때 현재 문서를 읽고,
작업 중 절차가 바뀌었다면 릴리스 후속 작업을 마치기 전에 다시 확인합니다.

## 1. 범위와 권한 확인

실제 저장소, 브랜치, worktree와 미완료 변경을 확인합니다. 무관한 작업을 보존하고 작업에 맞는 별도
브랜치를 사용합니다. 대상 스킬을 기록하고 미출시 변경, 버전 릴리스 준비, 이미 공개된 릴리스를 구분합니다.

파일 수정, 커밋, 푸시, 병합, 릴리스 작업과 외부 게시에 대해 이미 받은 승인을 확인합니다. 같은 대상의
같은 작업을 다시 승인받지 않습니다. 검토나 문서 작성 요청만으로 게시 권한까지 생기지는 않습니다.
추가 승인이 필요하다면 먼저 검토 가능한 초안과 검증을 준비하고, 부족한 권한만 요청합니다.

버전 릴리스 계획에는 필수 Announcements 공지와 블로그 처리 방안을 처음부터 포함해 구체적인 후속
작업까지 승인받을 수 있게 합니다. 공지 여부를 매번 다시 묻지 않습니다. 공개된 스킬 버전에는 공지가
필수입니다. 사용자가 더 좁은 범위를 지시하면 그 지시를 따릅니다.

## 2. 커밋·릴리스 전 문서 정합성 확인

설명을 실제 변경, 패키지 구성과 관측된 증거에 대조합니다. 해당하는 문서를 모두 확인하고,
수정하지 않아도 되는 문서는 이유를 기록합니다.

| 대상 | 확인할 내용 |
| --- | --- |
| 루트 `CHANGELOG.md` | 모든 변경에서 확인합니다. 스킬·문서·유지관리 절차의 의미 있는 변경을 기록합니다. 출시한 각 스킬의 이름·버전·변경 요약을 포함하며, 스킬별 changelog만 갱신해서는 안 됩니다. |
| `skills/<name>/SKILL.md`, 참조 문서, 스크립트, 자산 | 동작·제약·필수 자료와 패키지 구성이 일치해야 합니다. |
| 스킬별 `CHANGELOG.md` | 변경을 설명하고 미출시 작업과 공개 버전을 구분합니다. |
| 루트와 스킬별 README | 카탈로그, 사용 예, 제한, 지원 범위와 성숙도를 증거에 맞춥니다. |
| `docs/INSTALL.md`, 버전·검증 문서 | 설치 pin과 지원 구문을 실제 출시 상태에 맞춥니다. 미출시 대상을 설치 가능한 버전으로 안내하지 않습니다. |
| 예제, 검증 자료, 색인과 내부 링크 | 영향을 받는 예제와 링크를 갱신하고, 합성·과거·현재 증거를 구분합니다. |
| 영문·한국어 문서 | 주장·수치·버전·링크·조건·필수 행동을 같은 변경에서 맞춥니다. |

실제 파일명은 대소문자를 구분하는 루트 `CHANGELOG.md`입니다. 미출시 내용은 `Unreleased`에 두고
릴리스할 때 해당 공개·날짜 항목으로 옮깁니다. 제안 상태를 이미 출시한 것처럼 쓰지 않습니다.
의미에 영향이 없는 변경이라 갱신하지 않는 경우에만 완료 기록에 구체적인 이유를 남깁니다.

버전 증가 규칙을 임의로 만들거나 이 문서에 복제하지 않습니다. 버전 의미는 [VERSIONING.md](./VERSIONING.md),
실행 가능한 릴리스 검사는 [VALIDATION.md](./VALIDATION.md)를 따릅니다. 스킬 패키지 안의 문서도 릴리스
변경분일 수 있으므로, 문서 수정이라는 이유만으로 버전 검토를 생략하지 않습니다.

## 3. 검증과 릴리스 준비

공식 M1 저장소 검사(`PYTHONPATH=tools python3 -m skillstead_validate repo`)와 `git diff --check`를
실행합니다. 변경한 동작의 검사와 VALIDATION.md가 요구하는 추가 릴리스 검사도 수행합니다. 한국어
강조를 바꾸었다면 렌더링을 확인합니다. 통과·실패·미실행을 기록하며, 로컬 검사만으로 원격 CI·배포·
새 실행 환경 지원을 입증했다고 하지 않습니다. 스테이징이나 공개 전에 비공개 정보와 근거 없는 주장을 점검합니다.

게시 승인을 요청하기 전에 릴리스 노트, 버전 공지, 블로그 처리 방안이나 초안, 선택한 소셜 초안을
준비합니다. 기존 릴리스 도구와 실행 순서를 따르고 임의의 태그·Release 명령으로 대체하지 않습니다.
공개된 버전·태그 대상·Release URL·설치 pin을 검증한 뒤 사용 가능하다고 공지합니다. 내부 버전 수정이나
PR 병합만으로는 아직 공개 릴리스가 아닙니다.

## 4. 필수 버전 공지 게시

게시 위치: [블로그 저장소 Announcements](https://github.com/kyungseo/kyungseo.github.io/discussions/categories/announcements).

스킬 버전을 공개할 때마다 이 카테고리에 공지를 게시합니다. 문서만 바뀐 patch 릴리스도 포함합니다.
여러 스킬을 함께 출시했다면 모든 스킬·버전과 각 Release 링크를 적은 공지 하나로 묶을 수 있습니다.
스킬 버전 릴리스가 없는 저장소 자체 변경에는 필수 공지가 적용되지 않습니다.

1. 게시 전 해당 스킬·버전의 기존 Discussion을 검색합니다. 중단 후 재개할 때 같은 공지를 다시
   만들지 말고 기존 글을 확인하거나 수정합니다. 카테고리 ID를 절차에 고정하지 않고 실행할 때 확인합니다.
2. 출시한 스킬·버전, 사용자가 체감할 변화, 업데이트할 이유, 필요한 설치·마이그레이션 안내, 제한과
   검증된 Release·문서 링크를 담아 제목과 본문을 준비합니다. 임의의 성능 수치, 비공개 리뷰 출처,
   확인하지 않은 지원 주장을 넣지 않습니다.
3. 사용자가 승인한 게시 범위 안에서 실행합니다. 같은 작업을 이미 승인받았다면 진행하고, 아니라면
   준비한 초안을 제시해 부족한 게시 승인만 받습니다. 접근 권한이나 지시 때문에 게시할 수 없다면
   필수 단계를 조용히 생략하지 말고 장애와 다음 행동을 기록합니다.
4. 게시한 Discussion을 다시 읽어 URL과 공지한 버전을 기록합니다. 요청이 성공했더라도 해당 글을
   확인하지 못하면 게시 완료로 표시하지 않습니다. 성공 표시를 얻기 위해 게시를 반복하지 않습니다.

## 5. 관련 블로그 글 점검

버전 릴리스마다 [블로그 저장소](https://github.com/kyungseo/kyungseo.github.io)에서 관련 글을 찾습니다.
수정하기 전에 그 저장소의 현재 에이전트 지침을 읽습니다. 아래 중 하나를 선택하고 기록합니다.

- 설치 방법, 예제, 현재 제약이나 권장사항이 달라졌다면 기존 글을 수정합니다.
- 작업 방식의 큰 변화, 호환되지 않는 변경, 별도 설명이 필요한 주요 기능이라면 새 글을 검토하고
  개요나 초안을 준비합니다. 실제 발행은 승인된 범위에서만 합니다.
- 관련 글이 없거나 기존 주장의 의미에 영향이 없다면 그 이유를 기록하고 그대로 둡니다.

과거 경험과 검증 결과는 당시 기록으로 보존합니다. 새 버전에서 일어난 일처럼 고쳐 쓰기보다 필요하면
날짜가 있는 업데이트 주석을 붙입니다. 관련 언어판이 있으면 함께 맞춥니다. 승인된 발행 뒤에는 실제
공개 내용과 링크를 확인하고 수정한 글의 URL을 기록합니다. 버전 공지 승인만으로 블로그 발행 권한까지
생기지는 않습니다.

## 6. 소셜 초안은 필요할 때만 준비

소셜 게시는 선택 사항이며 사용자가 직접 합니다. 관련성이 있으면 짧게 바로 게시할 수 있는 초안을
제안하거나 준비합니다. 사용자가 원하지 않으면 생략하며 완료를 막지 않습니다. 이미 거절한 사항을
반복해서 묻지 않습니다. 플랫폼을 지정하지 않았다면 여러 채널별 자료를 늘리지 말고 짧은 초안 하나면
충분합니다. 검증한 링크를 사용하고, 미출시 변경을 소개한다면 미리보기임을 명시합니다.

이 절차를 근거로 소셜 계정에 직접 게시하지 않습니다. `drafted`, `declined`, `not-applicable` 중
상태와 짧은 이유를 기록합니다. 사용자의 실제 게시는 에이전트 작업의 완료 조건이 아닙니다.

## 7. 완료 기록과 안전한 재개

기존 변경·릴리스 PR 설명이나 Work 기록을 완료 기록으로 사용합니다. 별도 추적 체계를 만들지 말고
후속 기록이 있다면 링크로 연결합니다. 다음을 남깁니다.

- 대상 스킬, 해당하는 출시 버전, 커밋·PR과 Release URL
- 문서 정합성 결과: 루트 CHANGELOG 상태와 수정하지 않은 항목의 이유 포함
- 검증 결과, 증거의 한계와 남은 장애
- 공지 상태, 공지한 버전과 확인한 Discussion URL
- 블로그 처리 결과와 글·초안 URL 또는 그대로 둔 이유
- 소셜 초안 위치 또는 생략·비해당 이유
- 미완료 항목의 다음 행동과 담당자

`prepared`, `pending-authorization`, `blocked`, `published`, `not-applicable`처럼 상태를 정확히
씁니다. 변경 PR은 이후 버전 릴리스보다 먼저 끝날 수 있습니다. 그 경우 소통 작업을 `pending-release`로
표시하고 릴리스 기록으로 연결합니다. 저장소 자체 변경에는 릴리스 소통이 비해당인 이유를 기록합니다.
Release 공개와 릴리스 후속 작업 완료는 다릅니다. 필수 버전 공지가 없으면 후속 작업 전체를 완료로
표시하지 않습니다. 이미 성공한 릴리스를 되돌리거나 반복하지 말고 부분 완료를 보고합니다. 블로그 처리
판단은 기록해야 하며, 소셜 게시는 생략할 수 있습니다.

## 8. 절차 갱신

이 문서와 영문 기준 문서를 같은 리뷰 대상 변경에서 갱신합니다. 이유와 달라진 의무를 루트 CHANGELOG에
기록하고 갱신일을 바꿉니다. 진입점이나 PR 체크리스트의 링크·필드가 영향을 받으면 함께 수정합니다.
에이전트 진입점과 템플릿은 짧은 참조로 유지하고 별도의 절차 사본으로 만들지 않습니다. 버전 규칙과
실행 가능한 검사 정의는 기존 기준 문서에 둡니다.

새 규칙은 이후 작업과 아직 열려 있는 해당 단계에 적용합니다. 절차가 바뀌었다는 이유만으로 과거
릴리스를 다시 게시하거나 이전 공지를 소급 작성하지 않습니다. 과거 보완은 별도 계획으로 다룹니다.
작업 중 사용자가 요구를 바꾸면 범위 변경을 기록하고 최신 지시를 따릅니다.
