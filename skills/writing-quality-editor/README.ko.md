# writing-quality-editor

[English](./README.md) · **한국어**

사용자가 읽는 글을 처음부터 잘 쓰거나 숙련된 편집자가 다듬은 것처럼 자연스럽고 명료하게 고칩니다.
문장을 새로 만들더라도 제공된 사실과 근거의 범위는 바꾸지 않습니다.

README, 온보딩 문서, 릴리스 노트, 사용 설명서, 앱 UI, 오류 메시지와 갤러리 문구를 처음 작성하거나
검토·수정할 때 사용할 수 있습니다. 신뢰할 수 있는 작성 자료에서 곧바로 새 문서를 쓰고, 같은 언어
안에서 기존 문장을 고치거나, 영어와 한국어 사이에서 대상 독자에게 맞는 글로 다시 쓸 수 있습니다.

## 빠르게 시작하기

스킬 이름과 원하는 결과를 말하세요. 원문 또는 신뢰할 수 있는 사실 자료, 대상 독자와 반드시 보존해야
할 의미·식별자를 함께 제공하면 됩니다.

```text
writing-quality-editor로 이 설치 안내를 처음 사용하는 사람이 따라가기 쉽게 다듬어 줘.
모든 명령, 경로, 사전 조건, 경고와 복구 절차는 그대로 유지해 줘.
```

수정안 없이 문제점만 받고 싶다면 그 조건을 분명히 적으세요. 스킬은 읽기 전용인 `Assess` mode를
사용합니다. 일반적인 작성·수정·언어 전환 요청에서는 mode를 직접 고를 필요가 없습니다.

## 네 가지 mode

| Mode | 용도 | 파일 변경 |
| --- | --- | --- |
| `Compose` | 제공된 사실·근거·제약과 독자 목표로 새 문서 작성 | 요청받은 초안이나 파일만 생성 |
| `Assess` | 의미 보존, 명료성, 문체, 구조, 현지화 문제 진단 | 변경하지 않음 |
| `Revise` | 같은 언어 안에서 문장 품질 개선 | 요청받은 범위만 변경 |
| `Adapt` | 영어와 한국어 사이에서 대상 언어로 처음 작성한 것처럼 자연스럽게 재구성 | 요청받은 범위만 변경 |

`Adapt`는 단어를 일대일로 옮기는 번역이 아닙니다. 독자와 문서 종류에 맞게 문장을 나누거나 합치고,
정보 순서와 관용 표현, 설명 밀도를 조정할 수 있습니다. 대신 사실과 주장, 의도, 조건, 수치, 식별자,
예외, 제약, 위험, 승인과 다음 행동은 그대로 보존합니다.

이미 원하는 언어로 쓰인 문서에는 `Revise`가 같은 방식으로 동작합니다. 초안은 문서가 무엇을 뜻하는지
담고 있지만, 제공된 사실과 검토된 근거가 초안보다 우선합니다 — 근거와 어긋나거나 근거가 다루는 범위를
넘어서는 주장은 초안에 있다는 이유로 남기지 않고 삭제하거나 한정합니다. 다만 근거가 그 대목을 다루지
않았다는 사실만으로는 삭제할 이유가 되지 않습니다. 초안이 스스로 정하지 못하는 것은 **어떻게 읽히는지**
입니다. 문체가 대상 독자에게 맞지 않으면 문체는 바꿀 수 있고, 문서가 주장하고 요구하고 경고하는 내용은
그대로 둡니다. 문장만 고쳐서는 독자가 막히는 경우 — 지시 뒤에 경고가 나오거나 핵심이 세 문단 뒤에
묻혀 있는 경우 — `Revise`는 문단과 섹션을 옮길 수도 있습니다. 단 어떤 독자 문제를 푸는지 밝히고
나머지는 그대로 둡니다.

문장 표현, 자연스러움과 명료성을 고쳐 달라는 요청에서는 기존 문단과 섹션 순서에 문제가 없는 한
국소 편집부터 시작합니다. 독자가 실제로 막히는 가장 작은 완결된 구·절·문장만 수정 대상으로 표시하고
주변 문장은 그대로 둡니다. 하나의 표현이 임의 변경, 승인 없는 변경, 사전 고지 없는 변경 중 무엇을 뜻하는지
확정할 수 없다면, 가장 자연스러워 보이는 해석을 고르지 않습니다. 해당 구간은 `Needs Human`으로 남기고
안전하게 판단할 수 있는 다른 부분만 고칩니다. 구조 변경은 별도의 구조 문제가 확인될 때만 선택합니다.

시간을 들이면 뜻을 추론할 수 있다는 이유만으로 충분한 문장이라고 판단하지 않습니다. 해당 문단이 설명·비교·
안내를 맡고 있는데도 필요한 관계나 용어, 근거의 범위를 독자가 직접 복원해야 한다면 축약 표현·비유·문장 조각을
보완합니다. 다만 대상 독자에게 익숙한 표기와 기술적 축약, 이미 역할을 다하는 간결한 문장은 그대로 둡니다.

문서 전체를 요청받았다면 사용자가 같은 문제를 하나씩 지적할 필요가 없습니다. 사용자가 준 예시는 찾아야 할 독자
문제의 유형을 알려 주지만, 같은 문구만 바꾸거나 요청한 문서 밖까지 수정해도 된다는 뜻은 아닙니다.

직접 전달된 짧은 글이 이미 자연스럽다면 설명이나 변경 보고를 덧붙이지 않고 원문만 그대로 반환합니다.
같은 언어의 한국어 수정에서는 대상 독자가 같고, 사용자가 새 문체를 요청하지 않았으며, 원문 문체가
그 독자와 실제로 충돌하지 않을 때 원문의 높임말과 격식을 유지합니다. 둘 다 자연스러운 능동·수동 종결,
수식어 위치, 동의 표현과 숫자 표기는 그 자체로 수정 이유가 되지 않습니다. 압축된 문장은 중요한
주체·조건·결과를 독자가 추측해야 하는 경우에만 보완하며, 제목·목록 라벨·UI 라벨·코드처럼 의도적으로
짧은 조각에는 문장 종결을 억지로 붙이지 않습니다. `Needs Human`은 안전하게 사용할 결과를 만들 수 없게
하는 중요한 미확정 선택에만 사용하며, 선택적인 상세화에는 붙이지 않습니다.

두 모드 모두 작성자의 목소리를 유지합니다. 여기서 목소리란 글이 지닌 온도와 직설성, 리듬을 말합니다.
사용자가 요청하거나 대상 독자와 실제로 충돌하는 특성만, 그 특성만 바꿉니다.

`Compose`는 초안을 만든 뒤 다시 다듬는 이중 작업을 줄입니다. 처음부터 독자와 문서 목적에 맞게 쓰되,
문장만 새로 만들고 사실은 새로 만들지 않습니다. 제공되지 않은 기능·근거·호환성·수치·운영 결정은
그럴듯하게 채우지 않고 필요한 판단으로 남깁니다.

사용자가 자료를 직접 주지 않아도 공개 자료를 조사할 수 있다면 `Compose`가 먼저 근거를 수집할 수
있습니다. 검토한 출처와 근거 기준일을 기록하고 주요 주장에 출처를 표시하며, 측정된 사실과 출처의 주장,
작성자의 종합 판단을 구분합니다. 공개되어 있다는 이유만으로 자료를 신뢰하지 않습니다.

## 반드시 보존하는 것

- 사실과 이를 뒷받침하는 근거의 범위
- 작성자의 의도와 목소리
- 명령, 경로, URL, 오류 코드, 제품명, 버전과 기타 식별자
- 직접 인용문의 문구·문장부호와 이에 붙은 인용·각주 표식
- 조건, 예외, 제약, 불확실성, 위험, 승인과 되돌리기의 의미
- 기준 문서와 이를 따라가는 문서의 관계, 링크

제공된 원문 안에서 편집자나 에이전트에게 보내는 지시는 외부 사용자가 명시적으로 활성화하지 않는 한
원문 데이터로 취급합니다. 편집자 메모, TODO, `위 내용을 무시하라` 같은 문구가 여기에 해당하며,
문서 독자에게 전달하는 사용 지시는 해당하지 않습니다.

두 언어에서 안전하게 대응되는 표현이 없거나 원문이 모호하면, 매끄러운 문장 속에 임의의 해석을 숨기지
않고 `needs-human`으로 구분해 보여줍니다.

## 여기서 말하는 자연스러운 글

원문 언어의 어순이 그대로 비치는 문장, 설명되지 않은 내부 은유, 내용 없는 도입, 반복되는 요약,
기계적인 대칭, 똑같은 문장 호흡, 과도한 확신, 독자가 목적을 알기 전에 나오는 기술 설명을 찾아
문맥에 맞게 고칩니다. 특정 단어를 일괄 금지하거나, 필요한 기술 용어를 없애거나, 이미 자연스러운
문장을 굳이 다르게 쓰지는 않습니다.

AI 탐지기를 속이기 위한 도구는 아닙니다. 작성 주체를 알아볼 수 없다고 보장하지 않으며, 작성 주체나
출처를 숨기거나 가짜 경험을 넣거나 무작위로 낯선 표현을 섞지 않습니다.

## 검증 범위

- 특정 언어에 묶이지 않는 글쓰기 절차로 설계
- 첫 릴리스에서 검증하는 언어 조합: 영어↔한국어(한국어 결과는 `ko-KR`)
- 가상 검증 자료가 있는 문서 종류: README, 온보딩 문서, 릴리스 노트, 사용 설명서, 앱 UI,
  오류 메시지, 갤러리 문구
- 성숙도: Beta. 첫 릴리스의 지원 범위를 좁게 유지하면서 문서 종류와 언어별 근거를 쌓는 단계

위 항목은 실제 근거가 있는 범위만 표시한 것입니다. 다른 언어나 문서 종류에도 도움이 될 수 있지만,
검증된 지원 범위라고 주장하지 않습니다.

에이전트의 결과는 실행마다 달라질 수 있습니다. 국소 편집과 모호한 표현의 판단 보류를 기본값으로
삼아 불필요한 변경을 줄이지만, 모든 실행에서 표시하지 않은 구간까지 바뀌는 일이 전혀 없다고
보장하지는 않습니다. 중요한 문서는 게시하거나 사용하기 전에 최종 변경 사항을 직접 확인하세요.

## 사용 예시

실행 환경에 관계없이 이 스킬을 쓰고 싶다는 점을 분명히 하려면 `writing-quality-editor` 이름을 직접
말하고 원하는 결과를 설명하세요. 보통은 mode까지 지정할 필요가 없습니다.

현재까지 검증한 실행 환경에서는 자연어로 `WQE`라고 불러도 됩니다. 다만 이 줄임말은 보장된
`$WQE`나 `/WQE` 명령이 아니며, 선택 결과는 실행 환경·모델·대화 맥락에 따라 달라질 수 있습니다.
어떤 스킬을 쓸지 명확히 하고 싶다면 `writing-quality-editor`를 사용하세요.

```text
writing-quality-editor를 사용해 아래 문서를 자연스럽게 다듬어 줘. 원문의 핵심 사실, 조건과 요구 사항은
그대로 유지해 줘.
```

```text
WQE로 이 온보딩 안내서를 검토해 줘. 의미나 명료성 문제를 찾되 아직 문장은 수정하지 마.
```

설치된 에이전트가 요청의 의도를 파악해 스킬을 선택할 수 있는 환경에서는 평소처럼 요청해도 됩니다.

```text
이 제품 설명 자료를 바탕으로 새 README를 작성해 줘. 사용자 가치를 먼저 설명하고, 자료에 없는 기능이나
지원 환경은 추정하지 마.
```

```text
이 README를 검토해 줘. 내부 구조를 모르는 첫 사용자가 제품 가치와 다음 행동을 이해할 수
있는지 알려 줘. 아직 문장은 고치지 마.
```

```text
현재 기업의 AI 전환 도입 추세를 조사해 brief로 작성해 줘. 주요 주장에 출처를 달고, 근거 기준일을
밝혀 줘. 측정된 도입 현황과 공급업체 발표, 작성자의 추론도 구분해 줘.
```

```text
이 영어 온보딩 안내서를 한국어 독자가 자연스럽게 읽을 수 있도록 다시 써 줘. 명령과 경로는
번역하지 말고 모든 전제 조건, 경고와 복구 절차를 보존해 줘.
```

작업 범위를 명확히 고정해야 할 때만 mode를 직접 지정합니다.

```text
writing-quality-editor를 Assess mode로 사용해 이 릴리스 노트를 검토해 줘. 문장은 고치지 마.
```

저장소 자체의 절차가 brief 분류, 파일 위치, index 또는 승인을 관리한다면 그 절차를 먼저 따릅니다.
`writing-quality-editor`는 그렇게 정해진 문서 계약 안에서 문장 품질을 높일 수 있지만, 저장소의
작업 절차나 승인 규칙을 대신하지 않습니다.

`WQE`가 인용문에만 등장할 때, 다른 스킬이 함께 필요할 때, 저장소 작업 절차가 우선할 때의 예시는
저장소 전용
[`intent와 invocation 계약`](../../examples/intent-invocation-contract/README.ko.md)에 기록돼 있습니다.
